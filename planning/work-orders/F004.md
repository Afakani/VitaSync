## Ziel
Ein schneller Testbefehl je Anwendung und ein automatischer Prüflauf für jeden Pull Request. Der Lauf
muss scheitern, wenn ein Test fehlschlägt, ein Vertragsbeispiel nicht zum Schema passt oder eine
Abhängigkeitsregel aus `docs/Architektur.md` verletzt wird.

## Eingabe / Ausgabe / Fehlerfälle
- Eingabe: Repository-Stand eines Pull Requests.
- Ausgabe: automatischer Prüflauf mit vier Schritten (Struktur, API-Tests, Vertragsbeispiele, Importregeln).
- Fehlerfälle: fehlschlagender Test, ungültiges Vertragsbeispiel, verbotener Import, fehlende Abhängigkeit.

## Abnahmekriterien
- [ ] `pytest` für `apps/api` läuft in CI zusätzlich zum Strukturcheck.
- [ ] Die Beispiele in `contracts/` werden gegen ihr Schema geprüft – als Skript und in CI.
- [ ] Die Abhängigkeitsregeln aus `docs/Architektur.md` werden mit import-linter geprüft.
- [ ] Gegenprobe Vertrag: ein absichtlich falsches Beispiel lässt den Lauf scheitern.
- [ ] Gegenprobe Importregeln: ein verbotener Import lässt den Lauf scheitern.
- [ ] Gegenprobe Tests: ein absichtlich fehlschlagender Test lässt den Lauf scheitern (Briefing).
- [ ] Testbefehle stehen in `AGENTS.md` und `apps/api/AGENTS.md`; keine erfundenen Befehle.
- [ ] Alle Werkzeuge mit exakter Version gepinnt, `apps/api/requirements.lock` aktualisiert.
- [ ] Nur synthetische Fixtures.

## Tests
- `cd apps/api && .venv/Scripts/python.exe -m pytest`
- Vertragsprüfung über das neue Skript, Gut- und Fehlerfall
- import-linter, Gut- und Fehlerfall
- `python scripts/check_structure.py`
- Der CI-Lauf am Pull Request selbst
